# 作息表冲突解决（甲案）设计文档

> **设计日期**: 2026-09-24
> **项目**: Sleepy 课表 App
> **功能**: 编辑课表时绑定了共享作息表的情况下，修改作息内容的冲突处理

## 1. 问题背景

用户导入课表时，系统会创建一张共享作息表并自动绑定。现有行为 (`EditTableScreen.kt:331-340`) 是：用户在绑定状态下修改作息内容，系统会无声地将改动写入共享作息表 X，导致所有绑定 X 的课表一起被动修改——用户原本只想改自己这张。

**核心冲突**: 改本表作息 vs 改共享作息表

## 2. 状态模型与交互流程

### 2.1 编辑页维护的三类作息状态

```text
originalEffectiveSchedule   进入编辑页时实际生效的作息快照
draftEffectiveSchedule      用户当前正在编辑的作息草稿
pendingSchedulePolicy       无 / 改本表 / 新建独立作息表 / 同步 X
```

### 2.2 流程不变量

1. **未改作息**：只改名称、日期、周次 → 普通保存，不弹窗。
2. **改了作息，第一次保存**：只弹三选项，不写数据库。
3. **选择任一选项**：只记录 `pendingSchedulePolicy`，显示待执行提醒，回到编辑页，仍不写数据库。
4. **之后没有再改作息，再次保存**：执行已登记策略，并完成普通保存。
5. **选择后又改了作息**：旧策略失效；下一次保存重新弹三选项。
6. **点取消**：只把作息草稿恢复为 `originalEffectiveSchedule`，清除待执行策略，关闭弹窗；其他字段草稿保留，但不保存。
7. **三个选项始终显示**：
   - 改本表作息
   - 创建新的同名作息表
   - 同步更改作息表 X（影响数量仅用于提示，不隐藏）

### 2.3 流程图

```
编辑页
  |
  +-- 无作息变化 -- 保存 --> 普通保存
  |
  +-- 有作息变化 -- 保存 --> 三选项弹窗
                              |
             +----------------+----------------+
             |                |                |
          选项①            选项②            选项③
             |                |                |
             +------ 记录待执行策略 ---------+
                              |
                       回到编辑页 + 提醒
                              |
               +--------------+--------------+
               |                             |
        作息未再变化                    作息再次变化
               |                             |
          再次保存                    清除旧策略
               |                             |
        执行策略并入库              再次弹三选项

弹窗取消 --> 恢复作息原快照，保留其他字段草稿，不保存
```

## 3. 三个策略的作息数据行为

### 3.1 ① 改本表作息

- 以用户当前看到并编辑完成的 `draftEffectiveSchedule` 为准。
- 将它写入当前课表自己的内置作息字段。
- 清除当前课表的 `periodTableId`，变为"未绑定（使用本表作息）"。
- 原共享作息表 X 不改变。
- 其他绑定 X 的课表不受影响。

### 3.2 ② 创建新的同名作息表

- 以同一份 `draftEffectiveSchedule` 创建新的独立作息表。
- 新表名称基于当前课表名称生成；若名称已存在，使用既有的唯一名称递增规则。
- 当前课表改绑新表。
- X 不改变，其他绑定 X 的课表不受影响。
- 当前课表的内置作息快照仍保留原有语义。

### 3.3 ③ 同步更改作息表 X

- 将 `draftEffectiveSchedule` 写回 X。
- 当前课表继续绑定 X。
- 所有绑定 X 的课表读取到新的作息。
- 该选项始终存在；影响数量只用于提示，不改变行为。

### 3.4 数据源不变量

三个选项都使用同一份：

```
当前实际生效作息 + 用户本次编辑
```

不回退到导入时的旧快照，避免用户已经在共享表上做过的修改被旧数据覆盖。

### 3.5 保存原子性

真正再次保存时，所选策略对应的绑定关系和作息内容必须作为一个可撤回的操作完成：

- ①：写本表内置作息 + 解绑 X
- ②：创建新作息表 + 切换绑定
- ③：更新 X，保持绑定
- 任一操作失败时，不留下半完成的绑定或作息状态

## 4. UI 呈现与文案

### 4.1 弹窗（仅作息触发，BottomSheet）

```
这次作息改动要改到哪里？
当前作息：2024 秋季作息（另有 3 张课表绑定）

○ 只改本课表作息          本课表改用独立作息，不再跟随共享表
○ 新建独立作息表并绑定     以本课表名新建作息表，其他课表不受影响
● 同步更改「2024 秋季作息」 将影响另外 3 张课表

                          [ 取消 ]
```

- 无其他绑定者时第三项副文案改为"仅此课表使用该作息"。
- 第一项名称含共享表名，避免用户不知道同步目标是哪张。
- 「取消」= 撤销本次作息改动，其他字段草稿保留。

### 4.2 待执行提醒（登记策略后，编辑页常驻）

```
⚑ 待执行：新建独立作息表并绑定 · 再次保存后生效   [ 修改 ]
```

- 点「修改」= 重新弹三选项（不清空作息草稿）。
- 作息草稿再次变化 → 提醒条自动消失，策略作废，下次保存重弹。

### 4.3 文案规则

- 一律指向用户可见结果，不出现「解绑」「兼容列」「水合」等内部术语。
- 三个选项都不提课表名称/日期/周次，边界不外扩。
- 无作息改动路径完全不出现上述任何文案。

## 5. 技术锚点

### 5.1 Repository 层（已有方法，复用或扩展）

| 方法 | 用途 | 现状 |
|---|---|---|
| `updateTableMetadata(table, writeTimeDomain=false)` | 只写 name/startDate/maxWeek | 已有 |
| `updateTableMetadata(table, writeTimeDomain=true)` | 写元数据 + 时间域（解绑场景） | 已有 |
| `updateTableMetadataWithPeriodTable(table, periodTable)` | 元数据 + 共享作息表原子双写 | 已有 |
| `bindPeriodTable(tableId, null)` | 解绑 | 已有 |
| `bindPeriodTable(tableId, newId)` | 换绑 | 已有 |
| `copyPeriodTableAs(sourceId, newName)` | 复制作息表 | 已有 |
| `insertPeriodTable(entity)` | 新建作息表 | 已有 |
| `periodTableDao.getTablesBoundTo(periodTableId)` | 查绑定数量 | 需新增 |

### 5.2 ViewModel 层（待扩展）

- `EditTableViewModel` 新增状态：
  - `originalEffectiveSchedule: PeriodTableEntity?`
  - `draftEffectiveSchedule: PeriodTableEntity?`
  - `pendingSchedulePolicy: SchedulePolicy (NONE/DETACH_COPY/CREATE_NEW/SYNC)`
- 新增方法：
  - `hasScheduleChanged(): Boolean` — 比较 original vs draft
  - `selectPolicy(policy: SchedulePolicy)` — 登记待执行策略
  - `cancelPolicy()` — 清除策略，恢复 original
  - `clearPolicyIfScheduleChanged()` — 作息再次变化时清除旧策略

### 5.3 UI 层（待新增/修改）

- `EditTableScreen` 保存按钮逻辑：
  - 先判断 `hasScheduleChanged()`
  - 为 false → 走普通保存
  - 为 true → 检查 `pendingSchedulePolicy`
    - 若已有策略且作息未再变化 → 执行策略 + 普通保存
    - 若无策略或作息已再变化 → 弹三选项 BottomSheet
- 新增组件：
  - `ScheduleConflictBottomSheet` — 三选项弹窗
  - `PendingPolicyBanner` — 待执行提醒条

## 6. 测试覆盖

### 6.1 单元测试

| 场景 | 验证点 |
|---|---|
| 未改作息 → 保存 | 不弹窗，直接落库 |
| 改了作息 → 第一次保存 | 弹三选项，不写库 |
| 选择① → 再次保存 | 解绑 + 写本表内置，X 不变 |
| 选择② → 再次保存 | 新建表 + 改绑，X 不变 |
| 选择③ → 再次保存 | X 更新，所有绑定表读取新值 |
| 选择后取消 | 恢复原作息，其他字段草稿保留 |
| 选择后改作息 → 再次保存 | 重新弹三选项 |
| 选①后再次保存 | 执行策略 + 普通字段保存 |
| 选①后无作息变化再次保存 | 只执行策略，不弹窗 |

### 6.2 契约测试

- 三选项执行后 `notifyDataChanged()` 都被调用（widget 立即刷新）。
- 选①或②后，`updateTableMetadataWithPeriodTable` 不应被调用。
- 选③后，共享作息表内容更新，所有绑定表读取到新值。

## 7. 撤回（按既有 UndoManager 批边界）

- 选项①：批内绑定解绑 + 写内置列 → 一次撤回完整回退（绑定恢复、内置列恢复）。
- 选项②：批内建新表 + 绑定切换 → 一次撤回（删新表 + 绑定回旧 X）。
- 选项③：批内改 X + 元数据 → 一次撤回（X 内容回退 + 元数据回退）。
